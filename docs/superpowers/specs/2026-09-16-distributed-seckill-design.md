# 分布式秒杀系统设计（教学 Demo）

> 状态：待评审
> 日期：2026-09-16
> 定位：**接近真实架构的教学 Demo**，用于学习分布式秒杀的完整链路。
> 本文档描述的设计服务于学习目的，与真实生产系统存在明确差距，差距清单见第 11 节。

## 1. 背景与现状

当前项目 `D:\Java\TeProject` 已有一个**内存秒杀演示**：

- `SeckillInventoryService` 使用 `AtomicInteger` + CAS 扣减库存
- 接口 `POST /api/seckill/purchase`（无参数）、`GET /api/seckill/stock`
- 固定 100 库存、单商品、单实例、无持久化
- `docs/api/seckill.md` 已明确标注「不可直接作为生产秒杀方案使用」

本次工作将这个演示演进为一个分布式的、可多实例部署的秒杀系统。

## 2. 目标与非目标

### 目标

1. 在多实例部署下保证库存**不超卖**、**不少卖**
2. 支持**一人一单**限购
3. 支持**多商品**（每个活动独立库存）
4. DB 不处于抢购请求的关键路径上，以支撑万级 QPS 的架构形态
5. 提供可运行的并发测试与压测脚本，让学习者能**亲眼看到**不变量的成立与失效

### 非目标（本轮明确不做）

- 订单创建、支付、退款
- 秒杀时间窗口（开始/结束时间）
- 用户认证与鉴权（`userId` 由调用方直接提供，**不校验真实性**）
- 管理端（活动创建通过 SQL 种子数据预置）
- 多机房、异地多活、容灾切换

## 3. 需求约束（已与用户确认）

| 维度 | 结论 |
| --- | --- |
| 目标形态 | 生产级分布式架构（用于教学） |
| 业务范围 | 只到「抢购成功 / 失败」判定，不建订单、不接支付 |
| 用户模型 | 请求携带 `userId`，一人一单；不做认证 |
| 活动模型 | 多商品（`seckillId`），**无时间窗口**；活动由 `data.sql` 预置 |
| 并发量级 | 目标形态为万级 QPS；**验收以正确性指标为准，QPS 仅作观察数据** |
| 运行环境 | JDK 11、Spring Boot 2.7、Maven Wrapper；Docker 可用（Testcontainers） |

## 4. 方案选型

### 候选方案

**方案 A：Redis 权威库存 + MQ 异步落库** ⭐ 已选定

**方案 B：Redis 预扣 + DB 同步落库（DB 为准）**

- 一致性最强、组件最少，但 DB 留在关键路径，与万级 QPS 目标直接冲突
- 「回滚 Redis」本身可能失败，复杂度并未真正降低

**方案 C：Redis 权威库存 + 应用内异步队列**

- 少一个中间件，但内存队列在进程崩溃时丢消息，与「不少卖」冲突

### 选定理由

方案 A 多引入一个 RabbitMQ，换来的是可靠削峰与应用无状态水平扩展能力，这正是分布式秒杀应有的形态。方案 B 违背 QPS 约束，方案 C 的可靠性缺陷在「生产级」前提下不成立。

## 5. 架构

### 5.1 组件与状态归属

```
                    ┌─────────────────────────────────────┐
   POST /purchase   │  Spring Boot 应用（多实例，无状态）   │
   {seckillId,      │                                     │
    userId}    ────►│  ┌───────────────────────────────┐  │
                    │  │ Redis Lua 脚本（唯一不变量点） │  │
                    │  └───────────┬───────────────────┘  │
                    └──────────────┼──────────────────────┘
                                   │
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
        ┌──────────┐        ┌───────────┐       ┌─────────────┐
        │  Redis   │        │ RabbitMQ  │       │   MySQL     │
        │ 权威库存  │        │  削峰队列  │       │  持久化副本  │
        │ 限购集合  │        └─────┬─────┘       │  流水+对账   │
        └──────────┘              │             └─────▲───────┘
              ▲                   │                   │
              │            消费者（可独立部署）─────────┘
              │
              └──── 对账任务（定时比对 Redis 与 DB）────┘
```

| 状态 | 权威副本 | 理由 |
| --- | --- | --- |
| 实时库存 | **Redis** | 万级 QPS 下唯一能承载原子扣减的存储 |
| 限购关系 | **Redis** | O(1) 判断，且必须与扣减在同一次 Lua 中原子完成 |
| 持久化库存 / 流水 | **MySQL** | 重启恢复、审计、对账的依据 |

**冲突时以 Redis 为准。** Redis 扣减成功的那一刻用户已收到 `200 OK`，此后 DB 只能追赶，不能否决。

### 5.2 并发不变量

这四条是系统的正确性定义，所有实现与测试都围绕它们展开。

| 编号 | 不变量 | 由谁保证 |
| --- | --- | --- |
| **I1** | 任意 `seckillId` 的库存永不为负（不超卖） | Lua 内先判 `stock <= 0` 再 `DECR`，两步在同一原子脚本内 |
| **I2** | 任意 `(seckillId, userId)` 至多成功一次（一人一单） | Lua 内 `SISMEMBER` 前置判断 + DB 唯一索引兜底 |
| **I3** | 全局成功响应总数 ≤ 活动初始库存（不少卖） | Lua 原子性 + 对账任务兜底修复 |
| **I4** | `DB 已落库数 ≤ Redis 已扣减数 ≤ 初始库存`，且最终相等 | MQ 至少一次投递 + 消费幂等 + 对账 |

**系统承诺的是最终一致，不是强一致。** I4 中的异步窗口客观存在，不做掩饰。

## 6. 数据模型

### 6.1 Redis 键

| 键 | 类型 | 含义 |
| --- | --- | --- |
| `seckill:stock:{seckillId}` | String（整数） | 实时可售库存 |
| `seckill:bought:{seckillId}` | Set | 已成功购买的 `userId` |

两个键均使用 `{seckillId}` 作为 **hash tag**。这不是风格选择而是硬需求：Lua 脚本需同时操作两个键，Redis Cluster 下跨 slot 会直接报错。

**限购集合的容量问题**：集合大小等于活动库存上限，而非用户数——因为只有**成功购买**的用户才被写入。库存 1 万的活动中，集合最多 1 万个成员，内存占用可忽略。

### 6.2 Lua 脚本（唯一的不变量点）

```lua
-- KEYS[1] = seckill:stock:{id}      KEYS[2] = seckill:bought:{id}
-- ARGV[1] = userId
-- 返回 >=0: 成功，值为剩余库存；-1: 售罄；-2: 该用户已购；-3: 活动未预热
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then return -3 end
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -2 end
if stock <= 0 then return -1 end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return stock - 1
```

Redis 执行 Lua 是单线程的，「判断 + 扣减 + 记录」之间不存在其它请求插入的可能。**这是不使用分布式锁的原因**——锁能解决的问题，Lua 解决得更彻底。

**判空先于判限购**：顺序不可调换。若先查限购集合，一个未预热的活动会返回 `-2`（已购），把系统故障伪装成业务拒绝，用户和运维都会被误导。

### 6.3 MySQL 表

```sql
CREATE TABLE seckill_activity (
    id               BIGINT       NOT NULL AUTO_INCREMENT,
    name             VARCHAR(128) NOT NULL,
    initial_stock    INT          NOT NULL,
    remaining_stock  INT          NOT NULL,
    stock_updated_at DATETIME     NOT NULL,
    created_at       DATETIME     NOT NULL,
    PRIMARY KEY (id)
);

CREATE TABLE seckill_record (
    id         BIGINT      NOT NULL AUTO_INCREMENT,
    seckill_id BIGINT      NOT NULL,
    user_id    VARCHAR(64) NOT NULL,
    created_at DATETIME    NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_seckill_user (seckill_id, user_id)
);
```

**为什么同时保留 `remaining_stock` 冗余列与流水表**：冗余换取查询性能，代价是「两个字段需保持同步」。接受这个代价的理由是对账任务能把它变成**金丝雀**——正常情况下两者恒等，一旦分叉即说明代码或人工操作出了问题。

**为什么需要 `stock_updated_at`**：没有它，对账只能报「不一致」，无法区分两种截然不同的情况：

| 情况 | 表现 | 应对 |
| --- | --- | --- |
| 追赶中 | Redis 已扣 5000，DB 落后 200 | 正常，异步固有延迟，**不应告警** |
| 卡住了 | 落后 200 且 `stock_updated_at` 停滞超阈值 | 消费者故障，**必须告警** |

有了时间戳，告警条件从「数值不等」变为「数值不等 **且** 时间戳停滞」，从必然误报变为真正可用。

**`uk_seckill_user` 的作用**：它使 MQ 的「至少一次投递」成为可放心接受的前提——消费重复时 `INSERT` 撞唯一键，捕获 `DuplicateKeyException` 视为成功即可，无需额外幂等表。

### 6.4 消费者事务

```sql
INSERT INTO seckill_record (seckill_id, user_id, created_at) VALUES (?, ?, NOW());
UPDATE seckill_activity
   SET remaining_stock = remaining_stock - 1, stock_updated_at = NOW()
 WHERE id = ?;
```

两条语句在**同一事务**内执行。

**投递语义与 ack 策略**：

| 环节 | 策略 | 理由 |
| --- | --- | --- |
| 消费确认 | **手动 ack**，事务提交成功后才 ack | 自动 ack 在事务提交前就确认，进程此时崩溃即丢消息 |
| 处理失败 | 有限次重试（3 次，带退避） | 应对 DB 瞬时不可用 |
| 重试耗尽 | 投递到**死信队列**，不无限重投 | 无限重投会阻塞整个队列，拖垮其它活动 |
| 重复消息 | 捕获 `DuplicateKeyException` 视为成功并 ack | 唯一索引即幂等凭证，无需额外幂等表 |

**为什么选「至少一次」而非「至多一次」**：丢消息会造成「Redis 已扣减但 DB 无记录」，对账时表现为少卖，且**不可自动恢复**；重复消息只是被唯一索引挡掉，代价近乎为零。两者代价不对称，因此选前者。

## 7. 接口契约

### 7.1 接口定义

```
POST /api/seckill/activities/{seckillId}/purchase
Content-Type: application/json

{ "userId": "u_10086" }

GET  /api/seckill/activities/{seckillId}/stock
```

库存查询读取 **Redis**（权威副本），不查 DB——否则异步延迟会让用户看到「还有库存」却抢不到。

### 7.2 响应语义

| 场景 | HTTP | `code` | `message` |
| --- | --- | --- | --- |
| 抢购成功 | `200` | `"SUCCESS"` | 抢购成功 |
| 库存售罄 | `409` | `"STOCK_SOLD_OUT"` | 库存已售罄 |
| 该用户已购 | `409` | `"ALREADY_PURCHASED"` | 您已参与过本次秒杀 |
| 活动不存在 | `404` | `"SECKILL_NOT_FOUND"` | 秒杀活动不存在 |
| 服务未就绪 | `503` | `"NOT_READY"` | 秒杀服务暂不可用 |
| 参数非法 | `400` | `"INVALID_REQUEST"` | 参数校验失败 |

成功响应体：

```json
{ "code": "SUCCESS", "message": "抢购成功", "remainingStock": 99 }
```

库存查询接口的失败语义与抢购接口一致，复用同一套 `code`：

| 场景 | HTTP | `code` |
| --- | --- | --- |
| 查询成功 | `200` | `"SUCCESS"` |
| 活动不存在 | `404` | `"SECKILL_NOT_FOUND"` |
| 服务未就绪 | `503` | `"NOT_READY"` |

**「已购」使用 `409` 而非 `403`**：这不是权限问题而是资源状态冲突——同一 `(seckillId, userId)` 资源已存在。用 `409` 语义更准。附带效果是**接口天然幂等**：重复点击或网络重试不会造成二次扣减，只会稳定返回 `ALREADY_PURCHASED`。

**`404` 与 `503` 必须分开**：Lua 对「活动不存在」与「Redis 未预热」都返回 `-3`。若不区分，客户端传错 `seckillId` 会收到 `503`，把客户端错误伪装成服务端故障，误导排查方向。

区分方式：启动预热时**每个实例都**将有效活动 ID 载入内存 `Set<Long>`（活动为种子数据，量小且静态）。请求先查内存集合：

- ID 不在集合 → `404`（客户端问题）
- ID 在集合但 Redis 无 key → `503`（Redis 被清空 / 预热失败，运维问题）

**预热的分工**：所有实例都读 DB 建立内存集合，但**只有第一个用 `SETNX` 写 Redis**。`SETNX` 不是可有可无的优化——它保证应用重启时不会用 DB 的旧库存覆盖 Redis 中已扣减的实时库存。

### 7.3 本轮接口变更说明

- **替换**原有 `POST /api/seckill/purchase` 与 `GET /api/seckill/stock`。同一功能不应存在两套互相矛盾的事实。
- **统一 `code` 字段类型为字符串**。原契约中成功为数字 `0`、失败为字符串，同一字段两种类型迫使客户端分支判断类型才能解析。

## 8. 时序与失败处理

### 8.1 正常时序

```
客户端               应用实例                 Redis            RabbitMQ          MySQL
  │                    │                      │                  │                │
  ├─ POST purchase ───►│                      │                  │                │
  │  {userId}          ├─ 内存集合校验活动 ───►│                  │                │
  │                    ├─ EVAL Lua ──────────►│                  │                │
  │                    │   (SISMEMBER/DECR/   │                  │                │
  │                    │    SADD 原子完成)     │                  │                │
  │◄── 200 成功 ───────┤◄─ 返回剩余库存 ──────┤                  │                │
  │                    │                      │                  │                │
  │                    ├─ 发布消息 ───────────┼─────────────────►│                │
  │                    │                      │                  │                │
  │                                                    消费者 ───┤                │
  │                                                       (事务) ├─ INSERT ──────►│
  │                                                              ├─ UPDATE stock ►│
```

`200` 在 MQ 发布之前就已返回。Redis 扣减完成即为业务意义上的成功，落库是**补偿性**的而非**确认性**的。

### 8.2 失败矩阵

| 故障 | 表现 | 处理 | 用户看到 |
| --- | --- | --- | --- |
| Redis 不可用 | 无法判定库存 | **快速失败，不降级到 DB** | `503` |
| 活动不存在 | 内存集合未命中 | 直接拒绝，不进 Lua | `404` |
| 活动未预热 | 内存集合命中但 Redis 无 key | 告警 | `503` |
| DB 不可用 | 消费者写失败 | MQ 重试 + 消息积压 | `200`（不受影响） |
| 消费者宕机 | 消息积压 | MQ 保留消息，重启后续消费 | `200` |
| 消息重复投递 | 唯一索引冲突 | 捕获 `DuplicateKeyException` 视为成功 | `200` |

**「Redis 不可用不降级到 DB」的理由**：直觉上会想用 DB 兜底，但一旦部分请求走 Redis、部分走 DB，两个存储各自扣减，**I1 与 I3 立刻被破坏**，必然超卖。宁可整体不可用，也不让不变量失效。**可用性让位于正确性**，这是秒杀系统的根本取舍。

### 8.3 已知缺口：双写问题

若 Redis 扣减成功但 MQ 发布失败，用户已收到 `200`、库存已真实扣减，而落库消息丢失——这是一次静默数据丢失。

采用的处理方式：

- 应用侧同步重试若干次；仍失败则记录错误日志
- 依赖 A1 对账（Redis vs DB）发现不一致并告警

**这是刻意的取舍而非疏漏**：另一个可选方案是把 `XADD` 写入同一个 Lua 脚本（用 Redis Stream 替代 RabbitMQ），从物理上消除该缺口。选择保留缺口的原因是教学价值——双写问题是工程师必须亲自面对并学会「承认缺口 + 对账兜底」的一课，且 RabbitMQ 的技能迁移性显著高于 Redis Stream。

## 9. 对账任务

对账**只告警，不自动修数**。理由是用户已收到 `200`，任何一侧的自动改动都可能制造新的不一致；人工介入是刻意的选择。

| 编号 | 检查 | 告警条件 | 定位 |
| --- | --- | --- | --- |
| **A1** | `initial_stock - Redis 实时库存` ≠ `COUNT(records)` | 且 `stock_updated_at` 停滞超过阈值 | 主线不一致，真实可用 |
| **A2** | `COUNT(records)` ≠ `initial_stock - remaining_stock` | 一旦非 0 | 金丝雀，恒应为 0 |

A2 只在代码漏写字段或人工改数时才会触发——两条语句在同一事务内，正常情况下不可能分叉。它是一次 `COUNT` 成本换来的 bug 探测器，价值在于**几乎不误报**。

**阈值与频率**：对账每 10 秒执行一次；停滞阈值定为 60 秒（`stock_updated_at` 超过 60 秒未推进才判定为卡死）。两个值均可配置，不硬编码。

**为什么没有 A3**：初稿曾设想「Redis 库存 ≤ 0 却仍返回成功」的检查。但该情形在 Lua 脚本中不可能出现（`stock <= 0` 直接返回 `-1`，不执行 `DECR`），且**周期性对账任务观测不到这个瞬时状态**——它只能看到终态。真正能证伪它的是测试而非监控：T1 已断言 `成功数 == 初始库存` 且 `Redis 库存 == 0`，完整覆盖该场景。因此它作为不变量归入测试，而非伪装成一条无法实现的对账规则。

## 10. 测试策略

### 10.1 分层原则

**默认测试不得依赖 Docker**——教学项目里 `mvnw.cmd test` 必须永远可运行，否则会养成「测试是红的，忽略它」的习惯。

| 层 | 命令 | 依赖 | 内容 |
| --- | --- | --- | --- |
| 单元测试 | `mvnw.cmd test` | 无 | 错误码映射、参数校验、内存活动集合、Lua 脚本返回码到业务异常的映射 |
| 集成测试 | `mvnw.cmd test -Pit` | **Docker** | 真实 Redis / MySQL / RabbitMQ 下的 Lua 契约、并发与一致性 |

**Lua 脚本本身无法在单元测试里执行**——它必须运行在 Redis 中，因此「`-1`/`-2`/`-3` 分别对应售罄/已购/未预热」这一契约属于**集成测试**。单元测试能覆盖的只是**返回码到业务异常的映射函数**（纯 Java，给一个 `-2` 应产出 `ALREADY_PURCHASED`）。这条边界必须写清，否则会写出一个永远跑不通的「单元」测试。

使用 JUnit 5 `@Tag("integration")` 标记，默认 profile 的 surefire 配置 `excludedGroups` 排除，`it` profile 纳入。

### 10.2 不变量对应的测试

**T1 — 不超卖（I1、I3）**

- 初始库存 100，200 个不同用户同时并发抢占
- 使用 `ready` / `start` / `completed` 三个 `CountDownLatch` 制造真实竞争
- 断言：成功数 == 100；Redis 库存 == 0；DB 落库数 == 100（等待消费者追上后）

**T2 — 一人一单（I2）**

- 同一 `userId` 发起 100 个并发请求
- 断言：恰好 1 次 `SUCCESS`，其余 99 次均为 `ALREADY_PURCHASED`；Redis 限购集合大小为 1；DB records 恰 1 条

**T3 — 消费幂等（I2 的持久化兜底）**

- 向队列重复投递同一 `(seckillId, userId)` 消息 3 次
- 断言：DB records 仍为 1 条；`remaining_stock` 只被扣减 1 次
- 专测 `uk_seckill_user` 唯一索引与 `DuplicateKeyException` 处理路径

**T4 — 多实例一致性（分布式方案的真正证明）** ⭐

- 同一 JVM 内启动 2 个 Spring Context（不同端口），共享同一套 Testcontainers 容器
- 两个实例同时并发打压
- 断言：累计成功数 == 初始库存（全局不超卖）
- 同时验证预热 `SETNX` 在多实例下的行为

T4 是本设计中最有价值的测试。单实例测试用 `AtomicInteger` 也能通过，**只有多实例才能证明「分布式」真正成立**。

### 10.3 测试能力的诚实声明

`CountDownLatch` 并发测试是**概率性**的——它提高竞争概率，但不保证每次都撞上竞态。因此：

- 并发测试通过**重复执行（如 10 次）**增强置信度，而非跑一次即宣布正确
- **不承诺**这些测试能 100% 抓出所有并发 bug（没有任何测试能做到），只承诺它们能证伪上述四条不变量

### 10.4 容器复用

启用 `testcontainers.reuse.enable=true`，容器在开发机上常驻复用，避免每次测试都等待冷启动。

## 11. 与真实生产的差距清单

本设计是教学 Demo，以下为**刻意的简化**：

| 项 | 本 Demo | 真实生产 |
| --- | --- | --- |
| 用户认证 | 请求自带 `userId`，**不校验真实性** | 网关/过滤器统一鉴权，`userId` 不可伪造 |
| 风控与防刷 | 无 | 验证码、设备指纹、行为风控、IP 限流 |
| 秒杀时间窗口 | 无，创建即可抢 | 精确到毫秒的开始时间，定时开闸 |
| 活动管理 | `data.sql` 种子数据 | 管理后台、审核流程、库存回补 |
| 请求削峰 | RabbitMQ 单层 | 多级队列、动态限流、排队令牌 |
| 库存回补 | 无 | 超时未支付自动回滚库存 |
| 对账与补偿 | 定时任务告警 | 完整对账平台 + 自动补偿 + 人工工单 |
| 可观测性 | 日志 | 指标、链路追踪、实时大盘、告警分级 |
| 容灾 | 单 Redis | Redis 集群/哨兵、多活、故障演练 |
| 压测 | 单机脚本 | 分布式压测、全链路压测、容量规划 |

**最需要强调的一条**：`userId` 不经验证，意味着**任何人构造 `userId` 即可绕过一人一单**。这是安全边界，在真实系统中不可接受。

**关于 QPS 目标的现实预期**：在单台 Windows 笔记本 + Docker 化 Redis 的环境下，压出万级 QPS 的可能性很低，瓶颈会先出现在 Docker 网络、JVM 或压测工具自身。因此**验收标准定为正确性指标（不超卖、不少卖、多实例一致）**，QPS 仅作为观察数据如实记录，不设硬门槛。

## 附录 A：实施顺序（对 Docker 的依赖）

因 Docker 环境重装期间无法运行集成测试，实施顺序按依赖排列：

| 阶段 | 内容 | 需要 Docker |
| --- | --- | --- |
| 1 | 领域模型、错误码、返回码映射函数、配置类、内存活动集合 | 否 |
| 2 | Lua 脚本及其契约测试、预热（SETNX）、扣减服务 | **是** |
| 3 | MQ 生产者/消费者、DB 访问、对账任务 | **是** |
| 4 | T1–T4 并发测试、多实例测试、压测脚本 | **是** |

阶段 1 的产出可在无 Docker 环境下完成并验证；阶段 2 起均需 Docker 环境就绪。

**阶段 1 的范围刻意收窄**：它只包含纯 Java、可立即验证的部分。把 Lua 契约测试放在阶段 2 而非阶段 1，是因为脚本必须跑在 Redis 中——如果按「先写完再一起测」排期，阶段 1 会产出一批无法验证的代码，正是 `verification-before-completion` 要避免的情形。

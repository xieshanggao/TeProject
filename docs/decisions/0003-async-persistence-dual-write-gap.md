# ADR 0003：接受异步落库的双写缺口，用对账兜底

## 状态

已采纳

## 背景

Redis 扣减成功与消息投递不是同一个原子操作。若 Redis 扣减成功但消息
投递失败，用户已经收到 `200`、库存也真的扣减了，而落库消息丢失——
这是一次**静默的数据丢失**。这是异步方案的经典难题，没有免费的解法。

被放弃的方案：把消息写入（`XADD`）放进同一个 Lua 脚本，即用 Redis Stream
替代 RabbitMQ。投递与扣减由此落在同一原子操作内，缺口从物理上消失。
没有选它，是教学定位的取舍：双写问题是工程师必须亲自面对并学会
「承认缺口 + 对账兜底」的一课，而 RabbitMQ 的技能迁移性显著高于 Redis Stream。

## 决策

**接受该缺口**，采用三层兜底：

1. 应用侧同步重试投递，最多尝试 3 次（含首次，即最多重试 2 次）。
   次数有限是刻意的：用户此时已经拿到 `200` 并断开连接，在请求线程里
   无限重试只会耗尽 Web 容器线程，把局部故障放大成整体不可用。
2. 仍失败则记录 `error` 级别日志，写明「Redis 已扣减、用户已收到成功、
   MySQL 将缺少对应流水」。
3. 依赖 A1 对账（Redis 已扣减数 vs DB 已落库数）发现不一致并告警。

重试是安全的：唯一索引 `uk_seckill_user` 加「消费者把 `DuplicateKeyException`
视为成功」，决定了重复投递不会造成二次扣减。

## 影响

- 用户看到的仍然是 `200`，**投递失败不会把响应变成 500**。这不是疏忽：
  库存真的扣了，报 500 等于向用户报告一个与事实相反的结果，
  还会诱使客户端重试一次已经成功的抢购。
- 缺口**不能自愈**，只能靠对账发现、人工介入。因此对外承诺必须精确表述为
  「最终一致，且允许存在无法自动恢复的静默丢失」，不能写成「绝不丢消息」。
- 重试职责只放在一处：生产者**只投递、不重试、不吞异常**，重试由调用方
  （`SeckillService`）负责。若生产者自己重试并吞掉失败，调用方的重试分支
  就永远不会被触发，成为读起来像保护、实际不可达的死代码，
  两层重试还会相乘。

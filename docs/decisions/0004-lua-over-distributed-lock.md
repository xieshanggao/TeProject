# ADR 0004：用 Lua 脚本而非分布式锁保证并发不变量

## 状态

已采纳

## 背景

一次抢购要同时满足两个判断：该用户没买过（一人一单），且库存大于零。
两个判断与随后的两次写入必须**不可分割**——只要在「判断」与「写入」之间
留出窗口，两个并发请求就可能都读到「未购买、有库存」，然后双双扣减。

单实例时代这件事用 `synchronized` 或 CAS 就够了。多实例部署后锁必须跨进程，
本能的解法是分布式锁。以下是考虑过并放弃的方案：

- **Redis 分布式锁**（`SET NX PX` + 续期）：引入获取失败、超时、续期、
  误删他人锁等一整套失败模式；且锁本身仍落在 Redis 上，依赖没有减少，
  故障面却变大了。
- **数据库行锁**（`SELECT ... FOR UPDATE`）：把数据库拉回抢购关键路径，
  与 ADR 0002 的 QPS 目标直接冲突。
- **数据库乐观并发**（版本列 / 条件 `UPDATE`）：同样是数据库在关键路径上，
  高冲突下失败重试会形成风暴。
- **应用内锁**（`synchronized` / `ReentrantLock`）：只在本实例内有效，
  N 个实例就会卖出 N 倍库存——正是多实例测试要证伪的那个错误实现。

## 决策

**不加锁**，把「判断限购 → 判断库存 → 扣减 → 记录」写成一个 Lua 脚本，
用一次 `EVAL` 交给 Redis 执行。

理由是 Redis 执行脚本期间不会穿插其它命令（单线程执行模型）。
判断与写入之间不存在插入窗口——这不是「窗口很小」，是**没有窗口**。
锁要解决的问题，Lua 解决得更彻底。

## 影响

- 请求路径只有一次 Redis 往返，而分布式锁至少需要「获取 + 业务 + 释放」
  三次，获取失败还要重试。
- 少掉一整套失败模式：锁的获取超时、持有者崩溃后靠 TTL 过期导致的
  「两个持有者」窗口、业务未结束而锁已过期时的续期（watchdog）。
  这些坑每一个都能单独把不变量打破。
- 代价一：脚本内的键必须落在同一 slot，所以两个键都用 `{seckillId}`
  作为 hash tag。这是硬需求而非风格选择——Redis Cluster 下跨 slot 的
  `EVAL` 会直接报错。
- 代价二：部分业务逻辑从 Java 挪进了 Lua，调试与测试更麻烦。缓解方式是
  让脚本只做判断与算术、不承载业务语义，把返回码到异常的映射留在 Java，
  从而可以脱离 Redis 做单元测试。
- 代价三：脚本返回值只是一个整数，无法携带上下文。因此「活动不存在」与
  「未预热」共用一个返回码 `-3`，需要额外的内存注册表区分 404 与 503。

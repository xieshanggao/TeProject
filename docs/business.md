# 业务领域：订单管理示例

> 这是电商领域的示例。在依赖此文档前，请替换为本项目的实际业务知识。

## 目标

客户浏览商品、创建订单并支付，必要时可申请取消或退款。系统记录订单的完整生命周期，并确保状态流转合法。

## 术语表

| 术语 | 含义 | 示例 |
| --- | --- | --- |
| 客户 | 创建订单的用户。 | 张三购买键盘。 |
| 商品 | 可销售且具有价格与库存的物品。 | 机械键盘。 |
| 订单 | 客户购买一个或多个商品的请求。 | `ORD-20260729-001`。 |
| 订单项 | 订单中商品信息的快照。 | 键盘 2 件，单价 CNY 199。 |
| 支付 | 系统收取订单款项的记录。 | 微信支付 CNY 398。 |
| 退款 | 已支付订单取消后返还款项的记录。 | 退款 CNY 398。 |
| 订单金额 | 订单项价格之和，扣除优惠后、退款前的金额。 | CNY 398。 |

## 角色

| 角色 | 允许的操作 |
| --- | --- |
| 客户 | 创建、查看、支付和取消自己符合条件的订单。 |
| 管理员 | 查看所有订单，并依照独立规则处理异常情况。 |
| 支付服务商 | 向系统发送支付和退款结果。 |

## 订单生命周期

```text
PENDING_PAYMENT --pay--> PAID --fulfil--> COMPLETED
       |                    |
       cancel               cancel / refund
       v                    v
   CANCELLED            REFUNDING --refund succeeded--> REFUNDED
```

## 核心规则

1. 每笔订单至少有一个订单项，且只属于一个客户。
2. 创建订单时将商品名称和单价复制到订单项中；后续商品编辑不得改变历史订单。
3. 除非管理员规则明确允许，否则只有订单所属客户可以读取或操作订单。
4. 只有 `PENDING_PAYMENT` 订单可以直接取消。
5. 取消 `PAID` 订单时创建退款流程；订单不得立即变为 `REFUNDED`。
6. 支付或退款回调可能重复。多次处理不得产生重复资金流或状态变更。
7. 已完成、已取消和已退款的订单均为终态。

## 实现前需确认的开放问题

- 何时锁定和释放库存？
- 已支付订单在履约开始后是否仍可取消？
- 是否支持优惠、运费、税费或部分退款？
- 使用哪些支付服务商，回调验签规则是什么？

## 秒杀

秒杀是一个独立于上述订单领域的业务场景，用于演示高并发下的库存扣减。
它以「接近真实生产架构的教学 Demo」为定位，刻意保留了一些简化，
差距清单见 `docs/architecture.md`。

### 术语

| 术语 | 含义 | 示例 |
| --- | --- | --- |
| 秒杀活动 | 一次可被抢购的商品批次，拥有独立的库存。 | 活动 1，初始库存 100。 |
| 抢购 | 用户尝试从活动中获得一件商品的请求。 | 用户 `u_10086` 抢购活动 1。 |
| 限购 | 同一用户对同一活动至多成功一次的约束。 | 一人一单。 |
| 实时库存 | Redis 中当前可售的数量，是库存的权威副本。 | 剩余 99 件。 |
| 落库 | 把抢购结果异步写入数据库的过程。 | 消费者写入流水并扣减库存副本。 |

### 业务规则

1. 每个秒杀活动拥有独立库存，互不影响。
2. 每次抢购扣减 `1` 件。同一用户对同一活动至多成功一次。
3. 库存大于 `0` 时抢购可成功；库存为 `0` 时返回「售罄」。
4. 并发请求的成功总数不得超过活动初始库存（不超卖），也不得少于
   可售数量（不少卖）。
5. 抢购成功即不可撤销：即使后续落库失败，库存也不归还。
6. 库存以 Redis 为权威副本；数据库中的库存是异步副本，用于查询与对账。
7. 落库是异步的，因此数据库的库存与流水在任意时刻可能暂时落后于
   Redis，但最终一致。
8. 数据库中「库存副本已扣减的件数」（`initial_stock - remaining_stock`）与
   流水条数必须始终相等（二者在同一事务内更新）。一旦不等，说明存在
   代码缺陷或人工改数，对账任务会将其作为金丝雀告警（规则 A2）。

### 并发语义

实时库存与限购关系保存在 Redis 中，由单个 Lua 脚本原子完成
「判断限购 → 判断库存 → 扣减 → 记录」。因此：

- 系统在**多实例部署**下依然不超卖，库存权威副本不在应用内存中。
- Redis 扣减成功即返回 `200`；此时落库尚未完成。
- `remainingStock` 是接口处理时的实时快照，其他并发请求可能在其后继续扣减。

详细设计见 `docs/superpowers/specs/2026-09-16-distributed-seckill-design.md`。

### 不在范围内

不包含用户认证、订单创建、支付、退款、库存回补、秒杀时间窗口与风控反刷。
`userId` 由调用方直接提供且**不校验真实性**，这是教学 Demo 的刻意简化。
